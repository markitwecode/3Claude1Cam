## Chapter 1 · From tables and trees to graphs
Slug: ch1_graphs · ~10 min · Source: notes pp. 50–53 (§5 intro, Slides 94–101); handout pp. 100–108; recording 04:43–22:51. Background: notes pp. 14–15 (Slides 24–25), 38–39 (Slides 71–73), 43 (Slide 81).
Goal: explain why movie–person data is naturally a graph, describe the property graph model and how our movies become one, and store any property graph in two relational tables.
Scenes:
- s1_hook · Hook (~50 s): title card ("Graph Databases", "Databases · Lecture 5", "Part 1: from tables and trees to graphs"). Jennifer Lawrence and Daniel Radcliffe: never in a film together, yet a chain of co-stars links them (two vertices, a dashed "?" chain between). The destination of the lecture: one short query that gives every actor's distance to Kevin Bacon. Question: what shape is this data, and what query language fits that shape?
- s2_lasttime · Tables and trees (~100 s): the "last time" sentence (documents). From first principles, draw the many-to-many relationship itself: Charles Chaplin, Jackie Coogan, The Kid, The Gold Rush, lines between them. Relational: each line becomes a row of has_position (Chaplin's five rows for The Kid, Slide 25), and following a line is a join. Documents: cut the drawing into trees; The Kid's document holds copies of its people, Chaplin's holds copies of his movies, so every line is stored twice (Slide 73). Neither stores a line *as a line*. The third model does.
- s3_shapes · Data that forms a graph (~70 s): vertices (nodes) and edges (links, arcs, relationships). Slide 94's examples, one tiny drawing each, with the lecturer's questions: social network (friends of friends: whose likes to show you first), the web (links feed search ranking), roads (a maps app's route is a shortest path; edge = road, labelled with its length), package dependencies (all transitive dependencies), knowledge graphs (Wikidata, the infobox beside a Wikipedia article), our movies. Common thread: questions follow chains of edges, often of unknown length. Graph algorithms are the Algorithms course's job; ours is storing and querying.
- s4_propgraph · The property graph model (~105 s): build one vertex and one edge on screen. Vertex: one or more labels (Movie, Person); properties as key–value pairs, a little JSON object (usually flat). Edge: from one vertex to another (directed), exactly one type (ALL_CAPS by convention), its own properties. What the model allows: any vertex to any other, several edges between the same pair, and usually no schema (like documents: a property may be missing; nothing says which labels an edge type may join). The lecturer's point: it can express about what the relational model can; the difference is the query language.
- s5_moviegraph · Our movies as a graph (~95 s): Slide 97 built up: Jackie Coogan (birthyear 1914) and Charles Chaplin (1889) → The Kid (1921), The Gold Rush (1925); ACTED_IN with roles ([The Child], [A Tramp], [The Lone Prospector]); DIRECTED. Then all five of Chaplin's edges to The Kid appear (ACTED_IN, DIRECTED, PRODUCED, WROTE, COMPOSED_FOR): s2's five has_position rows. Every has_position row is one edge (49,811 both); plays_role folds into the roles list; genres are a list property (no Genre vertex: Exercise 22 questions that). Counts and the five types. Labels are nouns, types past-tense verbs; unlike tables, the model itself tells entities (vertices) from relationships (edges).
- s6_tables · A graph in two tables (~100 s): derive Slide 96 from "what must we store?": vertices(vertex_id, label, properties JSON) and edges(edge_id, tail_vertex, head_vertex, type, properties JSON), tail and head as foreign keys (one label per vertex is the slide's simplification). Then "what will we ask?": the edges out of a vertex and the edges into it, so two indexes (edges_tails, edges_heads), and a query can walk either way. Following one edge = a join with edges, then with vertices. Seven special-purpose tables vs two generic ones that hold any graph.
- s7_traverse · Graph databases and Traverse (~70 s): Neo4j, Memgraph, Amazon Neptune; relational databases are gaining graph features (as DuckDB gained JSON). We use Traverse: Cypher, runs in the browser (Neo4j needs Java and a server). Setup (Slides 98–101): download movies.tvdb; open traverse.truespar.com; delete the preloaded demo (also movies, but smaller and with different properties: cylinder icon, Delete, type "delete"); folder icon, "Upload .tvdb or .tvmodel". Or cypher-shell on the command line (same engine, tables but no picture).
- s8_recap · Recap (~40 s): recap visuals; next: asking questions with a query that looks like a drawing. (Split from s7 by the script-writer.)
Continuity: The Kid / Chaplin / Jackie Coogan / The Gold Rush is the house subgraph, reused in ch2 (r.roles), ch5 (SQL/PGQ) and ch6 (Exercise 20.1). The Lawrence–Radcliffe pair teased here is the running example of ch4–ch5. The m:n drawing of s2 returns in ch5's closing strip. Sets the visual conventions (Decisions).

## Chapter 2 · Patterns: vertices, edges and arrows
Slug: ch2_patterns · ~10 min · Source: notes pp. 53–55 (§5.1, Slides 102–105); handout pp. 109–112; recording 22:56–33:53.
Goal: read and write MATCH … RETURN queries for one vertex and one edge, explain a match as a placement of the pattern on the graph, and translate a one-edge pattern into SQL joins.
Scenes:
- s1_hook · Hook (~50 s): "last time" sentence. Which movies did Steven Spielberg direct? The SQL (Slide 105): three tables, two joins, and to read it you end up drawing person → has_position → movie. Question: what if the query *were* the drawing? Morph the drawing into `(p:Person {name: 'Steven Spielberg'}) -[:DIRECTED]-> (m:Movie)`.
- s2_vertex · Matching a vertex (~100 s): syntax read off a drawing: round brackets draw a circle; `m` names it (like a table alias); `:Movie` is its label. `MATCH (m:Movie) RETURN m.title` gives 2,935 rows; add m.year and m.genres (a list). RETURN ≈ SELECT; MATCH ≈ FROM and WHERE together. Filter with `WHERE m.title = 'The Kid' AND m.year = 1921`, or put the properties in curly braces (a JSON-like object): same row, The Kid, 1921, [Comedy, Drama, Family] (Slide 102). Keywords are case-insensitive, as in SQL.
- s3_match · What a match is (~90 s): the central idea, built visually: a pattern is a little graph with named holes; the database finds every placement of it on the big graph that respects labels, types, directions and properties; each placement is one row, its variables bound to what they landed on. One-vertex pattern: 2,935 placements; with the property map, one. A join also yields one row per matching combination: same idea. Teaser: the same name twice must land on the same vertex.
- s4_edge · Following an edge (~110 s): `(p:Person {name: 'Steven Spielberg'}) --> (m:Movie)`: any edge out of him gives 55 rows but only 35 distinct movies (derive: one row per placement, and on some movies he has several edges: E.T., directed and produced; A.I., also wrote). Add the type in square brackets, `-[:DIRECTED]->`: 28. "DIRECTED" is the type, not "directed graph" (every edge here has a direction). ORDER BY m.year LIMIT 4: Jaws 1975, Close Encounters of the Third Kind 1977, Raiders of the Lost Ark 1981, E.T. the Extra-Terrestrial 1982 (Slide 103).
- s5_props · Naming the edge, and its direction (~110 s): name before the colon, as for vertices: `-[r:ACTED_IN]->`; `r.roles` for The Kid (Slide 104: Albert Austin [Car Thief, Man in Shelter], B.F. Blinn [His Assistant], Beulah Bains [Bride], Carl Miller [The Man]); a list because one actor can play several parts (Keanu Reeves in The Matrix Resurrections: [Neo, Thomas Anderson]). `RETURN p, r, m` makes Traverse draw the matched subgraph (a star of Spielberg's films). Arrow forms: `<-[:DIRECTED]-` is an edge from m to p, so zero rows (every edge goes person → movie); `-[:DIRECTED]-` either direction; `-->` any type.
- s6_vssql · Cypher next to SQL (~100 s): Slide 105 side by side, colour-matched: `p` ↔ `people AS p`, the arrow ↔ `has_position AS hp` and its two ON conditions, `:DIRECTED` ↔ `hp.position = 'director'`, `m` ↔ `movies AS m`, RETURN ↔ SELECT. An edge in a pattern ≈ a join with has_position (in ch1's generic tables: with edges, then vertices). Same rows from DuckDB. Partly taste, but the SQL reader has to draw the diagram; in Cypher the query is the diagram.
- s7_recap · Recap (~60 s): one small visual per idea: circle ↔ `(m:Movie)`, a pattern placed on the graph, the arrow ↔ two joins, the three arrow forms. Next: two arrows into one movie, i.e. co-stars.
Continuity: Spielberg is this chapter's example; The Kid's cast returns from ch1. The placement picture of s3 is reused in ch3 (twins) and ch6 (Exercise 20.3).

## Chapter 3 · Co-stars: bigger patterns and counting
Slug: ch3_costars · ~9 min · Source: notes pp. 55–56 (Slide 106; the setting of Exercise 21); handout p. 113; recording 34:00–40:44.
Goal: match two edges meeting at one movie, explain why every pair appears twice and how `<` fixes it, predict the number of matches from the data, and aggregate in Cypher without GROUP BY.
Scenes:
- s1_hook · Hook (~55 s): "last time" sentence. Which pairs of actors have appeared together most often? What SQL needs, as a diagram rather than the full query (that's Exercise 21): has_position twice, people twice, three ON conditions. Question: what does "two actors, one movie" look like as a pattern?
- s2_twoedges · Two actors, one movie (~105 s): the lecturer's first version, two patterns separated by a comma sharing `m`: the same name means the same vertex; p1 and p2 are free to land anywhere. Then fold it into one line, `(p1:Person) -[:ACTED_IN]-> (m:Movie) <-[:ACTED_IN]- (p2:Person)`: the same query, drawn the way you'd draw it. Return the names and the title: The Kid's pairs, then the next movie's.
- s3_twins · Every pair twice (~105 s): derive it from symmetry: the pattern is its own mirror image, so swapping p1 and p2 in any placement gives another placement (Radcliffe–Watson and Watson–Radcliffe). With no condition: 261,476 rows, exactly 2 × 130,738. `p1 <> p2` still keeps both twins (261,476). `p1.person_id < p2.person_id`: of two different people exactly one order passes, so one row per pair and movie, and nobody pairs with themself.
- s4_predict · Predict the count (~85 s): reason before running: the database keeps only the top-billed cast, at most 10 actors per movie, so at most 45 pairs per movie and about 132,000 over 2,935 movies; the real count, 130,738, is exactly the sum of "k choose 2" over the movies (checked in DuckDB), in about a tenth of a second. A third co-star: a chain has only two ends at m, so add a third pattern sharing m (a star; patterns are any shape, not just lines); triples are the sum of "k choose 3", 347,841, about two seconds (the lecturer didn't dare run it).
- s5_aggregate · Counting without GROUP BY (~110 s): replace the title by `count(*) AS movies`, ORDER BY movies DESC, name1, name2 LIMIT 5: Radcliffe–Watson 8, Grint–Radcliffe 8, Grint–Watson 8, Depp–Bonham Carter 7, Downey Jr.–Johansson 7 (Slide 106). Derive the implicit grouping: with RETURN name1, name2, count(*), the only sensible thing to count is the rows sharing name1 and name2, so the non-aggregated RETURN expressions are the grouping keys (SQL makes you write them twice). count(*) here is the shared movies, one placement each. Only prominent cast is stored, so counts are lower than you might expect.
- s6_recap · Recap (~65 s): small visuals: the comma pattern folding into one line, the mirror twins, 45 pairs per movie, the triple star, the top-five table. Next: Lawrence and Radcliffe never shared a movie, so chains of co-stars of any length.
Continuity: the Harry Potter trio is this chapter's payoff; ch6 s5 (Exercise 21) writes the SQL sketched in s1, with the same top five.

## Chapter 4 · Paths of any length
Slug: ch4_paths · ~10 min · Source: notes pp. 56–57 (§5.2, Slide 107); handout p. 114; recording 40:44–45:53.
Goal: write variable-length path patterns, derive why paths between actors have even length, count paths by multiplying along the chain, and explain why path counts explode while the number of people levels off.
Scenes:
- s1_hook · Hook (~50 s): "last time" sentence. Lawrence and Radcliffe: the co-star pattern finds nothing. Six Degrees of Kevin Bacon: link any actor to Kevin Bacon through as short a chain of co-stars as possible. Question: how do you ask for a chain whose length you don't know?
- s2_chains · Chains of co-stars (~100 s): actors A, B, C: A and B share a movie, B and C another. Length 2 = co-stars; length 4 = a co-star in common. The arrows alternate (→ ← → ←), so drop the arrowheads: `-[:ACTED_IN]-` either way. `*4` after the type = four such edges in a row; `path =` names the whole path. Slide 107's query: 8.
- s3_even · Why the length is always even (~90 s): derive it: every edge joins a Person to a Movie (all five types go person → movie), so each step flips sides: person, movie, person… After k steps you are among the people exactly when k is even. So `*3` and `*5` find nothing, not by chance but by necessity (the lecturer ran `*3` live); `*2` finds nothing for a different reason (they never co-starred); `*4` 8, `*6` 495. The distance between two actors in movies is half the path length (Bacon numbers later).
- s4_count8 · Where the 8 comes from (~110 s): draw the 8 paths. Via Woody Harrelson: 3 Hunger Games films with Lawrence (Catching Fire, Mockingjay – Part 1, Part 2) × 1 with Radcliffe (Now You See Me 2). Via James McAvoy: 4 X-Men films (First Class, Days of Future Past, Apocalypse, Dark Phoenix) × 1 (Victor Frankenstein). Via Domhnall Gleeson: Mother! × Harry Potter and the Deathly Hallows: Part 2. 3×1 + 4×1 + 1×1 = 8: choices multiply along a path, alternatives through different middles add. That rule is why counts grow.
- s5_explode · The explosion (~120 s): ranges: `*2..6` gives 8 + 495 = 503; `*..4` up to four; a bare `*` any length. From Lawrence to anyone: 153, 12,160, 700,512, about 39.6 million paths of length 2, 4, 6, 8, but only 117, 3,985, 12,686, 14,072 different people at their ends, and only 14,581 actors are connected to her at all. Paths multiply by ~60–80 per extra co-star; people level off because there are only so many. Asking cypher-shell for all length-6 paths from her to anyone aborts. Detail: a path never reuses an edge but may revisit a vertex (112 length-4 paths lead from Lawrence back to herself). So a bare `*` can mean "a very large number of paths".
- s6_joins · Six joins (~80 s): in SQL every edge is a join: `*4` between two named actors means has_position four times; `*6` six; `*2..6` a UNION of three such queries. Painful but possible when the length is fixed. For "the shortest chain, however long", you don't know how many joins to write. Teaser for ch5 and next lecture.
- s7_recap · Recap (~65 s): small visuals: the alternating chain losing its arrowheads, the parity flip, 3×1 + 4×1 + 1×1, the paths-vs-people curves, the chain of joins. Next: of 503 paths we usually want one, the shortest.
Continuity: the Lawrence–Radcliffe pair and the "people vs paths" curves carry into ch5 (breadth-first search visits people, not paths). The parity rule justifies ch5's `length(path) / 2`.

## Chapter 5 · Shortest paths, Bacon numbers, and the graph languages
Slug: ch5_shortest · ~11 min · Source: notes pp. 57–59 (Slides 108–111, §5.3), Exercises 20–21 (p. 56) and 22 (p. 59); handout pp. 115–118; recording 45:53–57:19.
Goal: find shortest paths with shortestPath and allShortestPaths and say why that's cheap where listing all paths isn't, compute and read the Bacon-number query, place Cypher among GQL, SQL/PGQ and the others, and start on the exercises.
Scenes:
- s1_hook · Hook (~45 s): "last time" sentence (503 paths of length up to six between Lawrence and Radcliffe). Usually we want only the shortest. Question: can we find it without listing millions of paths?
- s2_bfs · Ripples: shortest paths (~100 s): breadth-first search as ripples from Lawrence: ring 1, her 117 co-stars (through her 17 films); ring 2, 3,895 more people, Radcliffe among them, so the shortest path has 4 edges. Each person joins once, in the first ring that reaches them, so the work grows with the graph, not with the number of paths (ch4's curves). Details: Algorithms course. Cypher: wrap the pattern in `shortestPath(…)` with a bare `*`; it returns one path, Lawrence → Mother! → Domhnall Gleeson → Harry Potter and the Deathly Hallows: Part 2 → Radcliffe. `allShortestPaths` returns all 8 of length 4, none longer.
- s3_unwrap · From a path to rows (~75 s): Slide 108's second half, one clause at a time: `nodes(path)` is the list of vertices; `WITH … AS vs` passes it on; `UNWIND range(0, size(vs) - 1) AS i` makes a row per position (like last lecture's unnest); `coalesce(vs[i].name, vs[i].title)` takes whichever property exists (people have names, movies titles: no schema). The step table 0–4. Or just RETURN path and let Traverse draw it.
- s4_bacon · Bacon numbers (~130 s): 0 is Kevin Bacon, 1 shared a film with him, 2 shares a co-star with him (Lawrence and Radcliffe are 2 apart); Erdős numbers do the same for mathematicians' papers. Read Slide 109 clause by clause: `allShortestPaths` from kb to every Person p; `WHERE p.person_id <> kb.person_id` leaves Kevin out; `length(path) / 2` (parity, ch4); `count(DISTINCT p.person_id)`, derived: allShortestPaths returns *every* shortest path, e.g. 8,631 people at number 3 are reached by 111,342 shortest paths; implicit grouping by bacon_number. About a minute to run. The histogram: 107, 3,519, 8,631, 1,676, 364, 212, 62, 9; 892 actors have no chain to him at all. (Lawrence's own Bacon number is 1: X-Men: First Class.) In SQL the number of joins depends on the data: recursive queries, next lecture.
- s5_languages · A family of graph languages (~80 s): Cypher, created at Neo4j around 2011, opened as openCypher; SPARQL (RDF triple stores, a different graph model), Gremlin; ISO standards based largely on Cypher: GQL (ISO/IEC 39075:2024, which Traverse also runs) and SQL/PGQ (SQL:2023 part 16). Slide 110's GQL: `SHORTEST 1` before the pattern, `-[:ACTED_IN]-+` for one or more edges (as + in a regular expression); returns length 4.
- s6_pgq · Graphs inside SQL (~90 s): "not examinable" badge on screen throughout. DuckDB's duckpgq extension (INSTALL … FROM community; LOAD; not in the web version). `CREATE PROPERTY GRAPH` translates tables into a graph: rows of movies and people are vertices, each plays_role row an edge via its foreign keys (has_position could be added too). `GRAPH_TABLE (… MATCH … COLUMNS (…))` turns the placements into a table the rest of SQL can use. Same rows as Slide 49's three-table join (The Kid: A Tramp / Charles Chaplin, Bride, Car Thief, His Assistant). Closes ch1's bridge (a graph stored in tables; now tables seen as a graph). SQL absorbs everything (JSON last time, graphs now), but pattern matching came from Cypher.
- s7_exercises · Your turn (~80 s): five hint cards (ch6 opens with the same cards). 20.1 Chaplin directed and acted: a name may appear twice. 20.2 the five busiest composers: COMPOSED_FOR and an implicit group. 20.3 both Wachowskis, any position: drop the type, then watch for repeats. 21 the co-star pairs in SQL: which table is the edge, and what plays the part of p1 < p2? 22 Romance and Comedy: a list property vs Genre vertices; think back to normalisation.
- s8_recap · Recap (~65 s): this chapter's visuals small (the ripples, the step table, the Bacon histogram, GQL's +, the GRAPH_TABLE bridge), then the lecture in one strip from ch1's m:n drawing: tables (a join per edge), trees (each relationship stored twice), graph (a pattern; paths of any length). Next time: recursive queries and Datalog, how SQL learns to follow chains of unknown length. End card.
Continuity: Lawrence–Radcliffe from ch4; the ripple rings become the Bacon histogram (both are BFS layers); The Kid's cast from ch1–ch2 in s6. Exercise cards shared with ch6 s1.

## Chapter 6 · Solutions to the exercises
Slug: ch6_solutions · ~9.5 min (bonus) · Source: notes pp. 56, 59 (Exercises 20–22); exercises PDF pp. 3–4; builds on ch2–ch5 and Lecture 4's normalisation (notes pp. 40–42, Slides 76–79).
Goal: worked solutions to Exercises 20–22, each run on the real databases, with the tempting wrong answers.
Scenes:
- s1_intro · Spoiler warning (~40 s): the five cards from ch5 s7; pause and try first.
- s2_chaplin · Exercise 20.1 (~85 s): `(p:Person {name: 'Charles Chaplin'}) -[:DIRECTED]-> (m:Movie) <-[:ACTED_IN]- (p)`: p twice, so both edges must leave the same vertex, a loop of two edges between p and m. The Kid 1921, The Gold Rush 1925, City Lights 1931, Modern Times 1936, The Great Dictator 1940. Equivalent: two comma patterns sharing p and m.
- s3_composers · Exercise 20.2 (~70 s): `(p:Person) -[:COMPOSED_FOR]-> (m:Movie) RETURN p.name, count(*) AS movies ORDER BY movies DESC LIMIT 5`: Hans Zimmer 72, James Newton Howard 52, Danny Elfman 49, John Williams 48, Marco Beltrami 42. Implicit grouping by name (by person_id is safer: see s5).
- s4_wachowski · Exercise 20.3 (~90 s): `(lana:Person {name: 'Lana Wachowski'}) --> (m:Movie) <-- (lilly:Person {name: 'Lilly Wachowski'})` gives 28 rows but 8 movies: derive it, each sister has several edges to most of these films, and every pairing of a Lana edge with a Lilly edge is a placement, so rows per movie multiply (The Matrix: 2 × 2 = 4; Cloud Atlas: 3 × 2 = 6; The Animatrix: 1 × 1). Fix: RETURN DISTINCT. Bound, The Matrix, The Matrix Reloaded, The Matrix Revolutions, The Animatrix, V for Vendetta, Cloud Atlas, The Matrix Resurrections.
- s5_sql · Exercise 21 (~120 s): build the SQL step by step: has_position h1 JOIN has_position h2 ON the movie, both position = 'actor', h1.person_id < h2.person_id, join people twice, GROUP BY, ORDER BY, LIMIT 5: the same top five as ch3. Pitfalls: plays_role instead of has_position counts characters, not movies (Matt Stone and Trey Parker come out on top with 51); grouping by name merges namesakes (23,179 people, 23,122 distinct names), so group by person_id too. Compare: one line of pattern vs four table references, three ON conditions, two position filters and an explicit GROUP BY.
- s6_genres · Exercise 22 (~120 s): design A (list property): `MATCH (m:Movie) WHERE 'Romance' IN m.genres AND 'Comedy' IN m.genres RETURN count(m)`: 174. Design B (Genre vertices): `MATCH (:Genre {name: 'Romance'}) <-[:HAS_GENRE]- (m:Movie) -[:HAS_GENRE]-> (:Genre {name: 'Comedy'}) RETURN count(m)`: 174 (run on a scratch copy where the Genre vertices were built from the lists: 23 genres, 7,826 edges). Trade-offs, in last lecture's terms: A keeps a movie in one vertex, but copies each genre name into every movie (renaming means many updates), and a genre with no movies can't exist: the relational database lists 26 genres, but Epic, Gothic and Experimental have no movies and appear nowhere in the graph (insertion and deletion anomalies). B stores each genre once, can carry genre properties, and makes "all movies of a genre" one hop from a vertex (genres become something to traverse through), for 7,826 more edges and a longer pattern.
- s7_recap · Recap (~60 s): one small visual per exercise and its lesson: the same name = the same vertex; implicit grouping; DISTINCT when edges multiply; one join per edge in SQL; list vs vertex is denormalised vs normalised. End card.
Continuity: cards match ch5 s7 (`scenes/ch5_s7_exercises.py`). Placement pictures from ch2 s3 explain s2 and s4.

## Decisions
- 6 chapters, ~60 min (50 core + a 9.5-min bonus), from a 52-minute lecture (04:43–57:19) whose notes chapter is only nine pages: the brief asks for first principles and derivations, which the slides state but don't derive (why even lengths, why counts explode, why DISTINCT, why `<`, why two indexes). Each core chapter answers one question: what is a graph (ch1), how does a pattern match (ch2), what happens with bigger patterns and counting (ch3), paths of unknown length (ch4), the shortest one and where Cypher stands (ch5).
