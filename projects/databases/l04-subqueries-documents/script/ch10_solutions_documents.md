[c10.choose.1] {card} Exercise seventeen. For each of five applications, would you store the data in tables, or as documents? Justify each answer, and for documents, say what each one contains. {pause} {stop} Pause here, and decide. {pause=1.5} {tests} Parts five and six gave us three questions. {shape} Is the data a tree, or a tangle? {writes} How often does it change, and how bad is it if two copies disagree? {kinds} And do all the items share one structure? {noanswer} The notes give no official answers, so the justification is what counts.

[c10.choose.2] {blog} First, a blogging platform. {post} A post, with its title, body, tags and comments, is a tree, since each comment belongs to one post. So, one document per post. {genres} The tags are an array of strings, just like our genres. {authors} The tangle is the readers, who comment on many posts. So each comment stores the reader's user ID, perhaps with a copied name, to update if they rename.

[c10.choose.3] {bank} Second, a bank. {transfers} Each transfer links two accounts, so this is a tangle. {copies} Store each transfer inside both account documents, and the two copies can disagree. Then money appears, or vanishes. {tables} In tables, a transfer is one row, from one account to another: one fact, one place. Balances change constantly, every account has the same structure, and the database checks every write. Tables win.

[c10.choose.4] {log} Third, an event log. {writeonce} Each event is written once and never changed, so there are no update anomalies to fear. {args} And each function takes different arguments, so the events come in many shapes. Documents fit perfectly: one per event, holding the time, the function's name, and an object of its arguments.

[c10.choose.5] {shop} Fourth, part six's online shop. {attrs} Books, shoes and TVs have different attributes, which schema-on-read handles well: one document per product. {hybrid} But orders and stock refer to products, and they suit tables. So a good answer is a hybrid: a products table with the shared columns, like name and price, plus a JSON column for the rest.

[c10.choose.6] {settings} Fifth, an app's settings. {onedoc} That's one small document per user, read in one go when the app starts, and referred to by nothing else. {versions} Each new version of the app adds settings, so old and new documents mix, and the app fills in a default for anything missing. {verdict} Documents again. {pause}

[c10.schema.1] {card} Exercise eighteen. Which of these properties of the people documents can a JSON schema enforce? {p1} Every person has a name. {p2} A death year is never earlier than the birth year. {p3} No two documents share a person ID. {p4} Every movie ID in acted in belongs to a real movie. {p5} And every movie title stored in a person document matches the movie's own title. {pause} {stop} Pause, and sort them. {pause=1.5}

[c10.schema.2] {view} Start from what a validator actually does. {one} It takes one document, and checks each value against a fixed rule: this key must be there, this value must be an integer, this string must match a pattern. {pause} {zones} So for each property, ask: does it need one value, two values, or other documents?

[c10.schema.3] {name} A name is one key, in one document. {required} The schema's required list demands it, and a document without one fails: name is a required property. So the first can be enforced. {empty} To rule out an empty name as well, give it a minimum length of one.

[c10.schema.4] {years} The death year needs two values. {fixed} A rule like minimum takes a fixed number, never another value from the document. So a death year before the birth year passes. {pause} {nostd} Standard JSON schema can't say it. Some validators add an extension for it, but other tools won't understand it.

[c10.schema.5] {across} The last three reach beyond one document, and the validator only ever sees one. {unique} Two documents with the same person ID each pass on their own. {key} In our database, the table's primary key does that job, outside the JSON. {pattern} The pattern on movie IDs checks that each looks like an ID, not that the movie exists. That's a foreign key's job. {titles} And a copied title drifting from the original is part five's update anomaly. No schema sees it. {pause}
