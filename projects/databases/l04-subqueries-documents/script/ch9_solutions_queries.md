[c9.pairs.3] {db} Here's a test database. The first table holds one row, one and ten. [c9.index.1] {card} Exercise fifteen. An index is redundancy too. The values of the column it covers are stored in the table, and again in the index. How is that like denormalisation, and how is it different? {consider} Think about consistency, reads and writes, and your queries. {pause} {stop} Pause, and think it through. {pause=1.5}

[c9.index.2] {alike} First, what they share. {copy} Both keep a second copy of facts that already exist. {reads} Both speed up some reads: the index finds a year's movies without a full scan, and a movie document needs no joins. {writes} Both slow down writes, since every copy must change. {derived} And both are derived data: drop the index, and the database rebuilds it from the table.

[c9.index.3] {levels} Now the differences. They all come from one picture in the notes' introduction: the logical level, what queries see, sits above the physical level, how the bytes are stored. That's called data independence. {below} An index lives below the line. {above} Denormalised copies live above it, in the data itself.

[c9.index.4] {who} So who keeps the copies consistent? {dbms} For an index, the database does, automatically, in the same write, so the index and the table always agree. {app} Denormalised copies are the application's job. It must find every copy, and if it misses one, or crashes halfway, the copies drift apart.

[c9.index.5] {queries} And the queries. {create} Create an index on year, and this query is written the same way, and returns the same row, The Kid. {speed} Only its speed can change. {docs} With denormalised data, the query itself changes: you read the name inside the document, instead of joining. {drift} And once copies drift, the answer depends on which copy you read.
