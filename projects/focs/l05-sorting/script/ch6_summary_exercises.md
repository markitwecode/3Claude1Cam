[c6.radix.1] {small} The notes end with a different kind of sort. If you have many small integers, you can sort them by their digits, without comparing any two of them. {radix} It's called radix sort, and it takes big O of N time. {contradict} But part one proved that sorting needs about N log N comparisons. So how can this be faster? {pause}

[c6.radix.2] {list} Here's an example: fifty-three, nineteen, fifty-one, thirty-seven, twelve, thirty-four. {buckets} Set out ten buckets, one for each digit, from zero to nine. {units} Deal each number into the bucket for its last digit. Fifty-three goes into bucket three, nineteen into bucket nine, and so on. {collect} Then collect the buckets in order, from zero to nine. {first} Fifty-one, twelve, fifty-three, thirty-four, thirty-seven, nineteen. That's sorted by the last digit only.

[c6.radix.3] {tens} Now deal them again, by the tens digit this time. {keep} Numbers in the same bucket stay in the order they arrived. So twelve stays ahead of nineteen, and fifty-one ahead of fifty-three, just as the first pass left them. {sorted} Collect again, and the list is sorted. {passes} Each pass looks at every number once. Two-digit numbers need two passes, so the time is big O of N. {pause}

[c6.radix.4] {never} Notice that no two numbers were ever compared. {bound} Part one's bound counts comparisons, so it says nothing about this sort. There's no contradiction. {catch} But there's a catch. The number of passes is the number of digits, so the time is linear only if the largest number is fixed in advance.

[c6.radix.5] {equal} Then, as N grows, more and more of the items must be equal. With numbers below a hundred, there are only a hundred different values. {digits} And to sort N different numbers, you'd need about log N digits, which brings back N log N. {special} So radix sort is a simple special case. {others} Many other sorts exist, and the exercises outline two of them. {pause}
